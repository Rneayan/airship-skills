# 작업 전 알아야 할 비직관적 제약

실제 운영에서 시간을 가장 많이 잡아먹은 항목들이다. 링크 구조가 맞는데도 동작이 갈리는 원인은 대부분 여기에 있다.

## 1. 지침 파일을 읽는 범위가 에이전트마다 다르다

일부 에이전트는 하위 폴더의 `AGENTS.md`를 **계층적으로** 읽고, 일부는 루트 파일만 읽는다.

- 하위 폴더에 규칙 본문을 두면 그 폴더를 계층적으로 읽는 에이전트만 규칙을 따른다. 다른 에이전트는 규칙이 있는지도 모른다.
- 하위 `AGENTS.md`는 **포인터 문서**로만 둔다. "이 폴더의 규칙은 루트 `AGENTS.md`의 해당 섹션에 있다" 정도.
- 편의를 위해 규칙 본문을 하위 파일에 복원하고 싶은 유혹이 반복해서 생긴다. 복원하지 않는다.

## 2. 에이전트 설정 폴더는 샌드박스에서 막힐 수 있다

에이전트가 자기 설정 폴더(예: 자신의 홈 설정 디렉터리)를 스스로 열지 못하는 경우가 있다. 폴더 접근 요청 자체가 거부되기도 한다.

- 링크 대상 폴더에 접근할 수 없는 에이전트에게 링크 작업을 시키지 않는다.
- 셸을 쓸 수 있는 쪽(전체 제어 권한이 있는 로컬 에이전트, 또는 사람의 터미널)에서 `--apply`를 돌린다.
- 원격·컨테이너 환경의 셸은 로컬 머신과 **다른 파일 시스템**이다. 마운트되지 않은 경로를 가리키는 심볼릭 링크는 그쪽에서 따라갈 수 없고, 로컬 셸(zsh 등)이나 로컬 CLI도 없을 수 있다. 링크 작업은 실제 링크가 존재하는 머신에서 한다.

## 3. 저장소를 원본으로 쓰면 저장소 이동이 곧 링크 붕괴다

`~/.agents/skills/<name>` 이 저장소 안 폴더로 가는 디렉터리 링크일 때, 저장소를 옮기거나 이름을 바꾸면 해당 스킬 전부가 한꺼번에 끊긴다.

- 저장소 이동 직후 `--apply` → `--verify`를 반드시 돌린다.
- `find -L` 계열 탐색은 **끊어진 링크를 조용히 건너뛴다.** 끊어진 링크는 별도로 검사해야 잡힌다. 동봉 스크립트는 이 검사를 따로 한다.

## 4. "다른 에이전트에서 가져오기"는 동기화가 아니라 스냅샷이다

한 에이전트가 다른 에이전트의 스킬을 불러오는 기능은 대개 그 시점의 **복사본**을 만든다. 자동 업데이트를 켜지 않는 한 원본과 갈라진다.

- 가져온 복사본을 동기화된 것으로 취급하지 않는다.
- 두 에이전트가 함께 써야 하는 스킬은 가져오기가 아니라 공용 계층 + 링크로 처리한다.

## 5. 검증 실패가 항상 링크 문제는 아니다

`--verify`의 지침 로딩 확인은 CLI를 실행한다. 샌드박스 제약이나 인증 만료로 CLI 실행 자체가 실패하면 링크가 멀쩡해도 FAIL이 뜬다.

- CLI 프로브 FAIL과 링크 FAIL을 구분한다. 링크 점검 결과가 모두 OK인데 프로브만 실패했다면 링크 문제가 아니다.
- 자동 프로브가 없는 에이전트는 새 세션에 검증 마커를 직접 물어 확인한다.

## 6. 동시 편집은 조용히 덮어쓴다

두 에이전트가 같은 파일을 동시에 만지면 나중에 쓴 쪽이 이긴다. 경고도, 충돌 표시도 없다.

- 일을 넘기기 전후로 인수인계 노트를 읽고 쓴다.
- 상대가 바꾼 파일은 손대기 전에 diff부터 본다.
- 긴 작업은 파일 단위로 소유권을 나눈다.

## 7. GUI 자동화로 다른 에이전트 앱을 조작할 때

한 에이전트에게 다른 에이전트 앱을 대신 조작시키는 경우, 앱마다 접근성 등급이 달라 클릭만 되고 입력은 안 되는 상황이 생긴다.

- 사이드바 클릭이 먹지 않으면 메뉴 막대 명령으로 우회한다.
- 입력창은 접근성 트리에서 텍스트 영역 역할로 찾고, 기존 내용을 덮어쓰는 옵션으로 입력한다.
- 설정 화면 내부 전환처럼 배경 제어로 안 되는 동작이 있다. 그럴 땐 화면 전체 제어가 필요하다.
- 자동화가 두 단계 이상 실패하면 반복하지 말고 사람에게 넘긴다.
